# New API Key 用量与请求记录查询站点

## Goal

在现有 New API 域名下提供一个无需账号登录的公开查询页。API Key 持有者输入自己的 Key 后，可以查看该 Key 的额度、消费与用量趋势，并分页浏览日志保留范围内的全部请求记录；功能随现有 New API 服务部署到 `ssh2`。

## Background

- New API 最新代码位于 `G:\Users\admin\Desktop\code\public-api`，后续设计、实现和验证均以该仓库为准。
- `ssh2` 已运行该项目的 Docker Compose 部署，生产目录为 `/opt/newapi`，使用 SQLite。
- 现有 Root 用量分析已经具备有界聚合、小时趋势、模型等筛选和分页能力；现有 Token 只读鉴权能够从 `Authorization` 解析当前 Key 并在服务端上下文中写入真实 `token_id`。
- 现有 Token 日志接口仅返回最近 1000 条且没有分页、总数或时间筛选，不能满足本需求。
- 原始请求体由独立的 Root-only 加密 Request Snapshot 管理，响应正文不是常规日志字段；本功能不开放这些内容。

## Requirements

### R1. 公开查询入口

- 在现有 New API 域名下提供公开路由 `/key-usage`。
- 页面不要求 New API 账号登录，也不建立额外账号或查询密码体系。
- 用户通过 API Key 完成只读身份验证；服务端必须根据鉴权上下文锁定当前 Key，不能信任客户端提交的用户 ID 或 Token ID。
- API Key 仅保存在当前页面运行内存中，不写入 URL、Cookie、`localStorage`、`sessionStorage`、React Query key、控制台日志或普通服务端日志。
- 刷新、关闭页面或主动更换 Key 后，需要重新输入 API Key。

### R2. 额度与用量分析

- 展示 Key 名称、已用额度、剩余额度、总额度、是否无限额度和有效期。
- 展示请求数、输入 Token、输出 Token、总 Token、缓存读取/写入 Token、缓存率和消费额度。
- 展示按小时聚合的用量趋势，以及按模型聚合的分页明细。
- 支持时间范围和模型筛选；不得暴露其他用户、其他 API Key 或渠道维度。
- 单次查询时间范围最多 90 天，默认使用当天范围；分页大小必须有上限。

### R3. 全部请求记录

- API Key 持有者可以在任意合法时间范围内分页遍历该 Key 在服务器日志保留周期内的全部记录，而不是仅查看最近 1000 条。
- 包含该 Key 对应的成功消费、失败请求及其他与请求结算相关的 Token 日志；Code-Agent 内部审计记录不属于用户请求列表。
- 支持时间、日志类型、模型、请求 ID和上游请求 ID筛选。
- 列表及详情可展示时间、状态、模型、输入/输出/缓存 Token、费用、耗时、流式状态、分组、请求 ID、上游请求 ID、错误原因和普通用户可见的计费详情。
- 不展示原始请求体、响应正文、客户端 IP、用户 ID、用户名、Token ID、完整 Token、渠道 ID/名称、管理员调试信息或操作审计信息。

### R4. 安全与错误行为

- 所有 Token 自查接口必须使用 `TokenAuthReadOnly`、关键接口限流和禁止缓存响应头。
- 无效或禁用 Key 返回清晰的未授权提示；被禁用的用户不能查询。
- 已过期或额度耗尽但未禁用的 Key仍可查询其历史只读数据，与现有 Token 只读鉴权语义保持一致。
- 客户端收到 API Key 相关的 401/403 时必须在当前页面显示错误，不得跳转到 New API 登录页。
- 更换或清除 API Key 后，必须清除上一 Key 的内存数据和查询缓存，避免同一浏览器会话内串数据。

### R5. 集成与部署

- 查询页和 Token 自查接口直接集成到 `public-api`，随现有 New API 镜像部署，不增加持有 Root 凭据的独立服务。
- 不新增数据库表或生产数据迁移；查询复用现有 Token 与 `LOG_DB.logs` 数据。
- 部署沿用 `ssh2` 的精确提交构建、唯一镜像标签、SQLite/Compose 备份、单服务切换、健康检查和失败回滚流程。
- 不覆盖或提交仓库中现有的未跟踪 `.trellis/workspace/pi/` 内容。

## Acceptance Criteria

- [ ] AC1（R1）：匿名访问 `/key-usage` 时直接看到 API Key 输入页，不要求登录。
- [ ] AC2（R1/R4）：有效 Key 只能读取自身数据；伪造查询参数不能读取其他 Key、用户或渠道数据。
- [ ] AC3（R1/R4）：API Key 不出现在 URL、持久化存储、React Query key 或日志中；刷新后需要重新输入。
- [ ] AC4（R2）：有效 Key 可查看额度状态、汇总指标、小时趋势和按模型分页明细，统计口径与现有 Usage Analysis 一致。
- [ ] AC5（R2）：用量查询支持时间和模型筛选，并拒绝反向时间、超过 90 天的范围及超大分页参数。
- [ ] AC6（R3）：用户可按页遍历所选时间范围内的全部 Token 请求日志，并按类型、模型和请求 ID筛选。
- [ ] AC7（R3）：列表和详情不包含请求/响应正文、IP、用户/Token/渠道标识或管理员专用字段。
- [ ] AC8（R4）：无效/禁用 Key、禁用用户、查询超时和数据库错误均有页内错误状态，不触发登录跳转或跨 Key 缓存泄漏。
- [ ] AC9（R5）：功能随现有 New API 容器部署到 `ssh2`；容器重启后可用，`/api/status` 健康，失败时能够恢复旧镜像与备份。

## Out of Scope

- API Key 创建、修改、充值、额度调整或用户管理。
- 保存、展示或下载原始请求体和响应正文。
- 展示客户端 IP、渠道内部信息、管理员审计或 Request Snapshot。
- 建立独立账号体系、独立域名、独立后端服务或管理员凭据代理。
- 修改调用方发送 AI 请求的方式或现有 Root Usage Analysis 的权限语义。

## Product Decisions

- 访问地址固定为现有域名的 `/key-usage`。
- 仅凭 API Key 查询，不要求登录。
- API Key 只在页面内存中存在，刷新后重新输入。
- “全部请求记录”指在日志保留周期内通过有界时间范围和服务端分页完整遍历，不进行一次性无界返回。
- 请求详情仅包含脱敏后的日志元数据、计费和错误信息；不展示正文与 IP。
